# Cloud SQL Dialects and Cost Optimisation (BigQuery)

## Introduction
When querying a local MySQL database on your machine, writing an inefficient query might cost you a few extra seconds of processing time. In a Cloud Data Warehouse like Google BigQuery, an inefficient query costs **actual money**. 

BigQuery operates on a serverless architecture where you are billed based on the amount of data processed (bytes read). Therefore, migrating to the cloud requires a fundamental shift in how you write and optimise your SQL. This module covers the nuances of BigQuery's SQL dialect and the architectural techniques used to keep query costs low.

---

## 1. BigQuery Standard SQL: The Nuances
BigQuery uses **Google Standard SQL**, which is highly compliant with ANSI SQL but has a few distinct differences compared to local relational databases like MySQL.

### A. The Hierarchy Naming Convention
In MySQL, you query a table directly. In BigQuery, tables belong to datasets, which belong to projects. You must explicitly reference this hierarchy using backticks (replaced with quotes here for formatting but standard in actual IDEs):

``` sql
SELECT 
    order_id, 
    customer_id 
FROM 
    `your-project-id.olist_dataset.orders`
WHERE 
    order_status = 'delivered';
```

### B. Complex Data Types (ARRAYS and STRUCTS)
Unlike traditional row-based SQL, BigQuery is designed to handle nested and repeated data (often ingested from JSON). 
* **ARRAY:** A list of items in a single row (e.g., a customer having multiple phone numbers). You use the `UNNEST()` function to flatten arrays into standard rows so you can analyse them.
* **STRUCT:** An object that contains multiple fields (like a dictionary in Python).

## 2. The Golden Rule: NEVER run `SELECT *`
In a local MySQL database, running `SELECT * FROM table LIMIT 10;` is harmless. The engine reads 10 rows and stops. **In BigQuery, this is a dangerous and expensive anti-pattern.**

### Why is it dangerous?
BigQuery uses **Columnar Storage**. It does not store data row-by-row; it stores it column-by-column. 

When you run `SELECT *`, BigQuery is forced to open and scan every single column in the entire table, regardless of the `LIMIT` clause. If you run `SELECT *` on a 500GB table and apply a `LIMIT 10`, BigQuery still scans all 500GB, and you are billed for 500GB.

### The Solution
Always specify exactly the columns you need.

``` sql
-- ❌ BAD: Scans every column, highly expensive.
SELECT * FROM `project.dataset.olist_orders`;

-- ✅ GOOD: Scans only two columns, highly cost-effective.
SELECT 
    order_id, 
    order_purchase_timestamp 
FROM 
    `project.dataset.olist_orders`;
```

## 3. Advanced Cost-Saving Techniques
When dealing with massive datasets, selecting specific columns is not enough. You must structure the table to minimise how much data the engine has to read. The two primary ways to do this are **Partitioning** and **Clustering**.

### A. Partitioning (Slicing by Time)
Partitioning divides a large table into smaller, manageable segments (partitions), usually based on a `DATE` or `TIMESTAMP` column. 

Instead of scanning the entire dataset to find sales from last month, BigQuery only scans the specific partition for that month, ignoring the rest of the table.

**Creating a Partitioned Table:**
``` sql
CREATE TABLE `project.dataset.partitioned_orders`
PARTITION BY DATE(order_purchase_timestamp)
AS
SELECT * FROM `project.dataset.olist_orders`;
```

**Querying a Partitioned Table:**
``` sql
-- BigQuery ONLY processes data from January 2018. It ignores all other years/months.
SELECT 
    order_id, 
    price 
FROM 
    `project.dataset.partitioned_orders`
WHERE 
    DATE(order_purchase_timestamp) >= '2018-01-01' 
    AND DATE(order_purchase_timestamp) <= '2018-01-31';
```

### B. Clustering (Sorting within Partitions)
While partitioning splits data into "folders" by date, clustering sorts the data *inside* those folders based on specific columns (like `customer_city` or `product_category`).

If you frequently filter or aggregate by a specific column, clustering tells BigQuery exactly where to find that data within the block, bypassing massive amounts of irrelevant data.

**Creating a Partitioned AND Clustered Table:**
``` sql
CREATE TABLE `project.dataset.optimised_orders`
PARTITION BY DATE(order_purchase_timestamp)
CLUSTER BY customer_city, product_category
AS
SELECT * FROM `project.dataset.olist_orders_joined`;
```

## 4. Query Optimisation Checklist
Before hitting "Run" in the BigQuery console, always verify these steps to ensure your query is optimised for both speed and cost:

1. **Check the Byte Estimator:** The BigQuery UI provides a real-time estimate of bytes processed before you execute. Use this as your primary feedback loop.
2. **Filter Early and Often:** Apply `WHERE` clauses as early as possible in your subqueries or CTEs to reduce the dataset size before applying heavy `JOIN` operations.
3. **Avoid Functions on Filtered Columns:** If you apply a function to a column in a `WHERE` clause (e.g., `WHERE LOWER(city) = 'sao paulo'`), BigQuery must compute that function for every row *before* filtering, which destroys performance.
4. **Use Materialised Views for Dashboards:** If your Power BI or Tableau dashboard hits the exact same aggregated metrics every day, create a Materialised View. BigQuery pre-computes the results, saving processing costs on repeated dashboard refreshes.
