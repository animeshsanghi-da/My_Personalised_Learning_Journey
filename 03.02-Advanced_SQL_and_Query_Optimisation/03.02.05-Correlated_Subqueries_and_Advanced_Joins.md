# Advanced SQL: Correlated Subqueries and Advanced Joins

As a Data Analyst or Business Intelligence Analyst, mastering standard `INNER` and `LEFT` joins is just the baseline. To extract deep business insights—especially when orchestrating ETL pipelines or analysing complex relational datasets—you need to understand how to compare a table against itself and how to execute row-by-row contextual calculations. 

This module covers three highly tested interview topics: **Correlated Subqueries**, **Self Joins**, and **Cross Joins**.

---

## 1. Standard Subqueries vs. Correlated Subqueries

To understand a correlated subquery, we must first contrast it with a standard subquery.

### The Standard Subquery (Executes Once)
A standard subquery is independent of the outer query. It runs completely, returns a result (or a set of results), and then the outer query uses that result.

**Example:** Find all orders in our e-commerce database that are larger than the overall average order value.

``` sql
SELECT order_id, customer_id, order_value
FROM orders
WHERE order_value > (
    -- This inner query runs exactly ONCE
    SELECT AVG(order_value) 
    FROM orders
);
```

### The Correlated Subquery (Executes Row-by-Row)
A correlated subquery is **dependent** on the outer query. It cannot run independently. The database must execute the inner query *once for every single row* evaluated by the outer query.

**Example:** Find all orders that are larger than the average order value **for that specific customer**.

``` sql
SELECT o1.order_id, o1.customer_id, o1.order_value
FROM orders o1
WHERE o1.order_value > (
    -- This inner query runs for EVERY row in o1
    SELECT AVG(o2.order_value)
    FROM orders o2
    WHERE o2.customer_id = o1.customer_id
);
```

**Performance Note:** Because correlated subqueries execute row-by-row, they can severely impact performance. If you are processing a massive dataset with 100,000+ rows (like the Olist e-commerce dataset), a correlated subquery can cause major bottlenecks in your MySQL database. In many cases, these can be optimised and rewritten using Window Functions or CTEs.

## 2. The Self Join

A Self Join is simply a standard join (`INNER` or `LEFT`), but you join a table to itself. To do this, you **must** use table aliases to tell MySQL to treat the single table as two distinct entities.

Self joins are typically used for hierarchical data or comparative analysis within the same column.

### Use Case A: Employee-Manager Hierarchy
If you have a single `employees` table where one column is `employee_id` and another is `manager_id`, you can find out who manages whom by joining the table to itself.

``` sql
SELECT 
    e.employee_name AS Employee,
    m.employee_name AS Manager
FROM employees e
LEFT JOIN employees m
    ON e.manager_id = m.employee_id;
```

### Use Case B: Finding Matching Attributes
Suppose you are analysing customer demographics across key target regions like Indore, Bengaluru, and Pune, and you want to find pairs of customers who live in the same city.

``` sql
SELECT 
    c1.customer_name AS Customer_1,
    c2.customer_name AS Customer_2,
    c1.city
FROM customers c1
INNER JOIN customers c2
    ON c1.city = c2.city
    AND c1.customer_id != c2.customer_id; -- Prevents matching a customer with themselves
```

## 3. The Cross Join (Cartesian Product)

A Cross Join returns the Cartesian product of two tables. This means it joins *every row* from the first table with *every row* from the second table. If Table A has 10 rows and Table B has 20 rows, the Cross Join will return 200 rows.

**Syntax:**
``` sql
SELECT * FROM table_a
CROSS JOIN table_b;
```

### Business Application: Generating Reporting Scaffolding
Cross Joins are rarely used for analytical math, but they are incredibly useful for structuring reports. 

If you are building a Power BI dashboard or Tableau visualisation and need a continuous trend line, missing data can break your visuals. If a product had zero sales in February, standard `GROUP BY` logic will just skip February entirely. 

To fix this, you can use a Cross Join to create a foundational grid of *all products* and *all months*, ensuring zero values are explicitly represented.

``` sql
-- 1. Create a grid of every product for every month
WITH reporting_grid AS (
    SELECT p.product_id, m.month_name
    FROM products p
    CROSS JOIN fiscal_months m
),

-- 2. Calculate actual sales (will have gaps)
monthly_sales AS (
    SELECT product_id, MONTHNAME(order_date) AS month_name, SUM(sales) AS total_sales
    FROM orders
    GROUP BY product_id, MONTHNAME(order_date)
)

-- 3. Join the actuals to the perfect grid to enforce zeros
SELECT 
    rg.product_id, 
    rg.month_name, 
    COALESCE(ms.total_sales, 0) AS total_sales
FROM reporting_grid rg
LEFT JOIN monthly_sales ms 
    ON rg.product_id = ms.product_id 
    AND rg.month_name = ms.month_name;
```

## Key Takeaways for Interviews
1. **Correlated Subqueries** are row-by-row operations. They are powerful for contextual row filtering but require careful optimisation on large datasets.
2. **Self Joins** require you to alias the same table twice. Always remember the `a.id != b.id` logic when finding pairs to avoid duplicate self-matches.
3. **Cross Joins** lack an `ON` clause because they multiply all rows. Use them strategically to build scaffolding for time-series visualisations.
