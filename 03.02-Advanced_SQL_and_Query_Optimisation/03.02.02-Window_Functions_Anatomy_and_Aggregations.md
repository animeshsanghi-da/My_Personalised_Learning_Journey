# Advanced SQL: Window Functions Anatomy and Aggregations

## Introduction: The "Group By" Dilemma
In standard SQL, when you use an aggregate function like `SUM()` or `AVG()` with a `GROUP BY` clause, you collapse your data. Multiple rows are compressed into a single summary row. 

But what if you want to analyse the aggregated total *alongside* the individual row details? What if you need to calculate a running total or a moving average without losing the context of the specific transaction?

This is exactly where **Window Functions** step in. They perform calculations across a set of table rows that are related to the current row, but *unlike standard aggregations, they do not cause rows to become grouped into a single output row*. The row-level detail is perfectly preserved.

---

## 1. The Anatomy of a Window Function

Every window function follows a specific structural blueprint using the `OVER()` clause. 

``` sql
SELECT 
    column_name,
    AGGREGATE_FUNCTION(column_name) OVER (
        [PARTITION BY column_name] 
        [ORDER BY column_name] 
        [Frame Clause (e.g., ROWS BETWEEN...)]
    ) AS window_result
FROM table_name;
```

### The Three Pillars of `OVER()`
1. **`OVER()`**: This is the trigger. It tells the SQL engine, "Treat the preceding function as a window function, not a standard aggregation." If left completely empty `OVER()`, the "window" is the entire result set.
2. **`PARTITION BY`**: This acts like `GROUP BY` but for the window. It divides the result set into distinct partitions (groups) where the function is applied independently.
3. **`ORDER BY`**: This determines the logical sequence of rows *within* each partition. This is absolutely critical for calculating running totals or moving averages.

---

## 2. Standard Aggregation vs. Window Aggregation

Let's look at a practical business scenario: We want to see the total sales for a specific region, but we also want to see every individual order in that region.

**The Problem with `GROUP BY`:**
``` sql
-- This fails if you try to include order_id without grouping by it, 
-- which defeats the purpose of getting a total per region.
SELECT order_id, region, SUM(sales_amount) 
FROM sales 
GROUP BY region; 
```

**The Solution with `OVER()`:**
``` sql
-- This returns every single order, and attaches the total regional sales to each row.
SELECT 
    order_id, 
    region, 
    sales_amount,
    SUM(sales_amount) OVER (PARTITION BY region) as total_regional_sales
FROM sales;
```

## 3. Rolling Aggregations (Running Totals)

A running total accumulates values row by row. To achieve this, you must introduce the `ORDER BY` clause inside your `OVER()` function. 

By adding `ORDER BY`, the window function calculates the sum from the start of the partition up to the *current row*.

``` sql
SELECT 
    order_date,
    customer_id,
    sales_amount,
    SUM(sales_amount) OVER (
        PARTITION BY customer_id 
        ORDER BY order_date
    ) AS customer_running_total
FROM sales;
```

**How it works computationally:**
1. SQL partitions the data by `customer_id`.
2. Within each customer's partition, it sorts the rows chronologically by `order_date`.
3. For row 1, the running total is just row 1's sales.
4. For row 2, the running total is row 1 + row 2.
5. The process resets completely when it hits a new `customer_id`.

## 4. Moving Averages and Frame Clauses

In business intelligence, a 7-day or 30-day moving average is standard for smoothing out volatile daily data. To do this, we use the **Frame Clause** (usually defined using `ROWS BETWEEN`).

If you want to calculate a 3-row moving average (the current row and the two preceding rows):

``` sql
SELECT 
    order_date,
    daily_revenue,
    AVG(daily_revenue) OVER (
        ORDER BY order_date
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS moving_avg_3_days
FROM daily_sales;
```

### Common Frame Definitions:
* `UNBOUNDED PRECEDING`: From the very first row of the partition.
* `CURRENT ROW`: The current row being evaluated.
* `UNBOUNDED FOLLOWING`: To the very last row of the partition.
* `[N] PRECEDING / FOLLOWING`: A specific number of rows before or after.

*Note: If you use `ORDER BY` without a frame clause, SQL defaults to `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` (which is why running totals work so seamlessly).*

## Summary Best Practices
1. **Performance Check:** Window functions process after the `WHERE` clause and standard `GROUP BY` clauses, just before the final `ORDER BY`. Keep this execution order in mind when building complex queries.
2. **Avoid Redundancy:** You can define a window once and use it multiple times using the `WINDOW` clause (in supported dialects like MySQL 8.0+ and PostgreSQL) to keep code DRY (Don't Repeat Yourself).
3. **Context is King:** Always use window functions when the business asks to compare an individual record against a wider group metric (e.g., "Show me how much this specific order contributed to the monthly total").
