# Advanced SQL: Query Optimisation and Best Practices

## Introduction
Writing a query that returns the correct result is only the first step in a Data Analyst's workflow. When dealing with enterprise-scale databases or 100,000+ row datasets (such as large e-commerce order logs), an inefficient query can lead to database timeouts, locked tables, and sluggish dashboard performance. 

Query optimisation is the practice of writing SQL in a way that minimises the computational load on the database engine. This module covers the core mechanics of how SQL executes, how to use indexes, and the best practices for writing high-performance code.

---

## 1. The Logical Execution Order of SQL
To optimise a query, you must understand how the database engine reads it. SQL is written declaratively (you write what you want), but the database executes it logically in a very specific order.

**The Written Order (How we type it):**
1. SELECT
2. FROM
3. JOIN
4. WHERE
5. GROUP BY
6. HAVING
7. ORDER BY
8. LIMIT

**The Logical Execution Order (How the engine processes it):**
1. **FROM & JOIN:** The engine first locates the base tables and joins them in memory.
2. **WHERE:** It immediately filters out rows that do not meet the condition.
3. **GROUP BY:** It aggregates the remaining data into groups.
4. **HAVING:** It filters the aggregated groups.
5. **SELECT:** It finally returns the specific columns requested.
6. **DISTINCT:** It removes duplicates (computationally heavy).
7. **ORDER BY:** It sorts the final result set.
8. **LIMIT / OFFSET:** It restricts the number of rows displayed.

**Optimisation Takeaway:** Because `WHERE` executes *before* `SELECT` and `GROUP BY`, filtering data as early as possible in the `WHERE` clause is the most effective way to speed up a query.

## 2. Indexing Basics: The Game Changer
Imagine looking for a specific topic in a 500-page textbook without a table of contents or an index; you would have to read every single page (a "Full Table Scan"). A database index works exactly like a book's index.

An **Index** is a distinct data structure (usually a B-Tree) that keeps a specific column sorted, allowing the database engine to find data rapidly without scanning the entire table.

### When to Create an Index:
* **Primary Keys:** Automatically indexed by default.
* **Foreign Keys:** Columns heavily used in `JOIN` conditions.
* **Highly Queried Columns:** Columns frequently used in `WHERE` or `ORDER BY` clauses (e.g., `order_date`, `customer_id`).

### How to Create an Index:
``` sql
-- Creating an index to speed up date-based filtering
CREATE INDEX idx_order_date ON orders(order_purchase_timestamp);
```

### The Cost of Indexing:
Indexes are not free. While they drastically speed up `SELECT` queries, they slow down `INSERT`, `UPDATE`, and `DELETE` operations because the index must be updated every time the data changes. Do not index every column.

## 3. Reading Execution Plans (The EXPLAIN Command)
Before running a heavy query on a 100,000+ row table, you should always check its execution plan. In MySQL, prefixing your query with `EXPLAIN` tells you *how* the database plans to execute it.

``` sql
EXPLAIN 
SELECT customer_id, order_status 
FROM orders 
WHERE order_purchase_timestamp > '2023-01-01';
```

### Key Columns in the EXPLAIN Output:
* **type:** This is crucial. 
  * `ALL`: Full Table Scan (Bad for large tables).
  * `index`: Full Index Scan (Better, but still heavy).
  * `ref` or `eq_ref`: Using an index to find specific rows (Excellent).
* **possible_keys:** The indexes the engine *could* use.
* **key:** The index the engine *actually* decided to use.
* **rows:** The estimated number of rows the engine needs to examine to return the result.

## 4. Best Practices for 100,000+ Row Datasets

### A. Avoid `SELECT *`
Returning unnecessary columns wastes memory and network bandwidth. Always specify the exact columns you need.
* **Bad:** `SELECT * FROM order_items;`
* **Good:** `SELECT order_id, product_id, price FROM order_items;`

### B. Write SARGable Queries
SARGable stands for *Search Argument Able*. It means writing `WHERE` clauses in a way that allows the database engine to use indexes. **Do not wrap indexed columns in functions.**
* **Bad (Non-SARGable - Ignores Index):** ``` sql
  WHERE YEAR(order_date) = 2023
  ```
* **Good (SARGable - Uses Index):** ``` sql
  WHERE order_date >= '2023-01-01' AND order_date < '2024-01-01'
  ```

### C. Use `EXISTS` Instead of `IN` for Subqueries
When checking for existence against a very large secondary table, `EXISTS` is generally faster than `IN` because `EXISTS` stops searching the moment it finds the first match, whereas `IN` evaluates all results.

``` sql
-- Highly efficient for large datasets
SELECT customer_id 
FROM customers c
WHERE EXISTS (
    SELECT 1 
    FROM orders o 
    WHERE o.customer_id = c.customer_id
);
```

### D. Avoid Deep Pagination (OFFSET)
Using `LIMIT` and `OFFSET` for pagination is common, but deep offsets (e.g., `OFFSET 50000`) require the engine to process and discard 50,000 rows before returning the result. 
* **Optimised approach:** Use a cursor or filter by the last seen ID.
  ``` sql
  WHERE order_id > 50000 LIMIT 100;
  ```

### E. Beware of `DISTINCT` and `ORDER BY`
Both commands force the database to perform heavy sorting operations in memory. Only use `DISTINCT` when absolutely necessary (often, duplicate data implies an issue with your `JOIN` logic). If you must use `ORDER BY`, try to sort on an indexed column.

## Summary Checklist for the Data Analyst
Before deploying a script or connecting a BI tool (like Tableau or Power BI) to a live query, ask yourself:
1. Did I filter out unneeded rows as early as possible?
2. Are my `JOIN` conditions using indexed columns?
3. Did I avoid using functions on columns in my `WHERE` clause?
4. Have I tested the query logic using `EXPLAIN` to ensure no unexpected Full Table Scans are occurring?
