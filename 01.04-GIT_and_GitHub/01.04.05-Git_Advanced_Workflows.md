# Advanced Git Workflows: History Rewriting, Cherry-Picking, and Conflict Mitigation

## Overview
While basic Git operations manage daily snapshots, professional software development and production-grade data engineering require precise control over repository history. Advanced version control allows engineers to clean up messy local commits before publishing code, port individual hotfixes across environments, and safely recover from destructive updates. This module establishes complete mastery over production git mechanics.

---

## 1. Interactive Rebasing (`git rebase -i`)
Interactive rebasing allows you to rewrite, reorder, modify, or aggregate linear commit histories before sharing your development branch with an engineering team. This prevents uninformative logs like "fixed typo" or "bugfix 2" from entering the permanent master timeline.

### Execution Framework
To modify the last $N$ commits on your active branch, initiate the interactive session:
```bash
git rebase -i HEAD~4
```

Executing this command opens an environment containing a top-down list of target commits, prefixed with operational commands.

### Key Operational Sub-commands
* `pick`: Retain the commit exactly as it is.
* `reword`: Keep the commit contents but rewrite the log message.
* `edit`: Halt the rebase at this commit to allow modifications, file additions, or part-splitting.
* `squash`: Meld the commit content directly into the previous commit, combining log messages.
* `fixup`: Meld the commit content into the previous commit but completely discard its message log.
* `drop`: Remove the commit entirely from the branch timeline.

### Real-World Workflow Example: Squashing Pipeline Commits
Assume your local history looks like this:
```text
pick a1b2c3d Model training iteration 1
pick e5f6g7h Oops forgot to drop column X
pick i9j0k1l Adjusted hyperparameters
pick m3n4o5p Final clean run of regression model
```

To clean up this history for peer review, change the prefixes to absorb the mid-development fixes into a single clean commit:
```text
pick a1b2c3d Production Pipeline: Integrated Regression Modeling with hyperparameter adjustments
fixup e5f6g7h
fixup i9j0k1l
fixup m3n4o5p
```
Save and close the interface. Git automatically rewrites history linearly into a single consolidated entry.

## 2. Cherry-Picking Specific Commits (`git cherry-pick`)
Cherry-picking allows you to extract an isolated commit from any branch in the repository and cleanly apply it to your current active branch without performing an invasive merge or rebase of the entire parent sequence.

### Production Scenario
You are developing an experimental deep learning architecture on the branch `experimental-llm`. During research, you write an optimized GPU memory initialization fix (`commit c7a2b9f`). You need this hotfix instantly on your stable `main` production branch without dragging along the unverified neural network code.



### Implementation Commands
```bash
# Switch to the stable target branch
git checkout main

# Extract and apply only the target hotfix commit
git cherry-pick c7a2b9f
```

If structural conflicts occur during application, resolve the localized file disruptions manually, stage the changes, and continue:
```bash
git add .
git cherry-pick --continue
```

## 3. Git Reflog: The Repository Safety Net (`git reflog`)
Unlike `git log`, which displays only the public history of the current branch, `git reflog` logs every single system movement—including branch switching, resets, rebases, and deleted commits. If you mistakenly execute a destructive hard reset, `reflog` allows you to reverse it.

### Disaster Recovery Blueprint
You accidentally perform a hard destructive reset and lose three critical script modifications:
```bash
git reset --hard HEAD~3
```

To recover the missing references, query the local transaction registry:
```bash
git reflog
```

Output log format:
```text
7a1b2c3 HEAD@{0}: reset: moving to HEAD~3
9f8e7d6 HEAD@{1}: commit: ML_Pipelines: Optimized data scaling vector transformations
4c3b2a1 HEAD@{2}: commit: WebDev_API: Built jsonified inference endpoint fallback
```

Identify the structural position right before the error (`HEAD@{1}`) and restore the entire ecosystem precisely to that state:
```bash
git reset --hard 9f8e7d6
```

## 4. Tagging and Release Control
Tags act as unchanging pointers to specific historical milestones within your deployment cycle, typically tracking software releases (Semantic Versioning: Major.Minor.Patch).

### Lightweight vs. Annotated Tags
* **Lightweight Tags:** Purely local bookmarks referencing a commit.
* **Annotated Tags:** Stored as complete objects in the Git database, tracking the tagger's identity, email, cryptographic signatures, date, and description.

### Production Commands
```bash
# Create an annotated release tag on the latest stable master commit
git tag -a v1.0.0 -m "Production release for core data analytics and model serving API"

# Push release tags upstream to remote environments
git push origin v1.0.0

# Push all local development tags to remote systems at once
git push origin --tags
```

## 5. Advanced Conflict Mitigation: Ours vs. Theirs
During complex multi-developer merges, automated algorithms sometimes fail to resolve file line discrepancies. Advanced git flags enable tactical text overwrites based on operational targets.

When checking out conflicting branches or merging code, you can dictate absolute priority to one side of the conflict:
```bash
# Keep the changes from your current branch, discarding incoming conflicts
git checkout --ours data/feature_store.py

# Accept the incoming branch changes completely, discarding your local modifications
git checkout --theirs data/feature_store.py

# Finalize the tracking state
git add data/feature_store.py
git commit -m "Resolved versioning discrepancy via localized branch prioritization"
```
