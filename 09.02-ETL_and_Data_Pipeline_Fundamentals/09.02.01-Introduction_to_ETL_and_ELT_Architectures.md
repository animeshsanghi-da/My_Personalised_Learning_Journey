# ETL and ELT Architectures: The Foundation of Data Pipelines

## Introduction
In previous modules, the focus has heavily been on how to analyse and create visualisations from data that is already relatively clean or accessible via local files (such as the Olist dataset) or local databases. However, in enterprise environments, a Business Intelligence or Data Analyst rarely finds data sitting perfectly in one centralized location. 

Business data is generated everywhere: application databases, external APIs, CRM systems, and flat files. The process of moving this raw data from its source, cleaning it, and placing it into a structured storage system for analysis is governed by data pipelines. Understanding the architecture behind these pipelines is a critical bridge between data analysis and data engineering.

## What is ETL? (Extract, Transform, Load)
ETL is the traditional methodology for integrating data. 

1. **Extract:** Data is pulled from various source systems (e.g., extracting transaction records via an API or querying a remote SQL database).
2. **Transform:** The data is cleaned, filtered, aggregated, and formatted on a separate processing server. This is where tools like Python and Pandas are often utilized to handle complex, memory-intensive transformations before the data ever reaches its final destination.
3. **Load:** The perfectly structured and transformed data is loaded into the target database (like MySQL) or a Data Warehouse, ready for consumption by BI tools.

**When it is used:** ETL is ideal for legacy systems or on-premise environments where storage and compute power in the destination database are limited. The heavy lifting of data processing is done *before* the data arrives at its final storage location.

## What is ELT? (Extract, Load, Transform)
ELT is the modern standard, driven by the massive compute power and scalability of cloud technologies.

1. **Extract:** Data is pulled from source systems.
2. **Load:** The raw, unaltered data is immediately loaded into the target storage system (usually a Data Lake or a cloud Data Warehouse) without prior transformation.
3. **Transform:** The transformation happens *inside* the target database using the database's own compute power. This often involves writing the transformation logic entirely in SQL rather than relying on external Python scripts.

**When it is used:** ELT is the standard for modern data stacks. It allows for significantly faster ingestion of massive datasets because the pipeline isn't bottlenecked by a separate transformation server in the middle. 

## Storage Systems: Data Warehouse vs. Data Lake

Understanding where the pipeline delivers the data is just as important as how the data gets there. 

### Data Warehouse
* **Structure:** Highly structured and relational (Schema-on-Write). Data must fit a predefined, rigid model before it can be stored.
* **Data Type:** Clean, processed, and organized data (both historical and current).
* **Primary Users:** Business Intelligence Analysts and Data Analysts.
* **Tools:** Traditional relational databases or cloud-based warehouse solutions.
* **Use Case:** Feeding directly into dashboards (like Tableau or Power BI) for daily business reporting, structured querying, and calculating precise business metrics.

### Data Lake
* **Structure:** Flat architecture, storing data in its raw, native format (Schema-on-Read). Structure is only applied later when the data is actively queried.
* **Data Type:** Structured, semi-structured (JSON, XML), and unstructured (images, text logs).
* **Primary Users:** Data Scientists and Data Engineers.
* **Tools:** Cloud object storage.
* **Use Case:** Machine learning model training, deep exploratory data analysis on raw logs, and cheaply archiving massive volumes of historical data.

## The Modern Data Stack
For a data professional transitioning into pipeline development, a modern workflow typically involves:
* **Ingestion/Extraction:** Python scripts or automated integration tools moving data from source to destination.
* **Storage:** A hybrid approach where Cloud Data Lakes (for raw data) eventually feed curated subsets of data into Data Warehouses (for structured reporting).
* **Transformation:** SQL-based tools running directly in the warehouse, or Python/Pandas scripts for highly specialized algorithmic processing.
* **Orchestration:** Tools (which will be covered in later files) designed to schedule, monitor, and manage these scripts so they run autonomously without human intervention.
